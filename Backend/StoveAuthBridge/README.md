# MazeParty STOVE 인증 브리지

Node.js 24, 외부 npm 의존성 없음. SDK 사용자 토큰을 STOVE 서버 API로 검증하고 UGS Custom ID 토큰과 10분 유효 참가 증명을 발급한다. 게임 클라이언트와 같은 머신에 배포하는 구조가 아니라 운영자만 관리하는 HTTPS 서버가 필요하다. 현재 배포된 서버는 없다.

## 로컬 준비

1. 이 폴더에서 `.env.example`을 `.env`로 복사한다.
2. `node keygen.mjs`를 실행한다. `grant-private.pem`은 서버에만 보관한다. 출력한 공개 `grantKeyModulus`만 Unity 로컬 설정에 넣는다. 기존 키를 덮어쓰지 않으며 운영 중 재생성하면 배포된 클라이언트 설정도 함께 교체해야 한다.
3. `.env`에 STOVE 서버 API 자격증명, UGS 프로젝트와 환경 ID/이름, `Player Authentication Token Issuer` 서비스 계정 키를 입력한다. `STOVE_ID_FIELD`는 STOVE 담당자가 확인한 `guid` 또는 `member_no`로 고정하고 운영 중 변경하지 않는다.
4. `node --test`로 모의 API 및 로컬 HTTP 테스트를 실행한다.
5. `node --env-file=.env server.mjs`로 실행한다. 기본은 루프백 8080이다. `/healthz`는 프로세스 생존 검사이며 외부 인증 설정 성공을 보증하지 않는다.

## HTTPS 배포

관리형 컨테이너 서비스 또는 TLS 역방향 프록시가 있는 서버에 배포한다. Dockerfile은 실행 소스만 복사하며 `.env`/개인키는 이미지에 넣지 않는다. 환경 변수와 읽기 전용 Secret 파일로 주입한다. 컨테이너는 일반 사용자로 실행되며 프록시 내부 포트만 공개한다. 인증 주소는 `/v1/stove/auth`다. Unity 클라이언트는 HTTPS만 허용하고 리디렉션을 따라가지 않는다.

프록시에서 원본 IP 기반 제한·본문 12 KiB 제한·TLS를 적용하고 토큰/본문/Authorization을 로그에서 제외한다. 앱은 `X-Forwarded-For`를 신뢰하지 않고 소켓 IP당 분당 30건, 동시 16건을 제한한다. 단일 프록시 뒤에서는 모든 요청이 같은 소켓 IP이므로 앱 제한이 전체 사용자에 적용된다. 실제 배포 전에 신뢰 프록시 설정을 명시한 분산 제한 저장소/게이트웨이 제한으로 조정하고 부하를 검증한다. 다중 인스턴스에서도 메모리 제한만으로 전역 제한을 보장할 수 없다.

테스트와 Live 각각 별도 배포/키/UGS 환경을 사용한다. STOVE API 주소와 자격증명은 담당자가 발급한 환경을 사용한다. `https://api.onstove.com`은 공식 문서의 Live 예시이며 Sandbox 주소를 임의로 추측해 넣지 않는다.

## 검증 범위

`POST /v1/stove/auth`는 `{ "stoveAccessToken": "…", "publicKey": "RSA modulus base64" }`만 받는다. STOVE ID, 기존 UGS 토큰, 플랫폼/환경 선택을 클라이언트에서 받지 않는다. 서버 검증 결과의 64비트 사용자 식별자는 정밀도를 유지한다. 고정된 namespace·Game ID·환경·STOVE ID를 해시한 Custom ID로 출시 계정을 새로 만든다.

응답의 UGS access/session 토큰은 HTTPS로 해당 클라이언트에만 보낸다. 서버는 사용자 토큰을 저장하지 않는다. 방장에게 전달하는 별도 참가 증명에는 계정 ID·공개키 해시·환경·만료만 포함하고 서버 RSA 키로 서명한다. 게임 클라이언트는 별도 프로세스 개인키로 방/버전/시각/nonce를 서명한다.

STOVE 서버 API 토큰은 만료 전 갱신하며 40101/40103에 한 번 재발급한다. UGS 서비스 토큰은 짧게 캐시한다. 서비스 오류 응답을 외부에 전달하지 않는다. 외부 API 타임아웃·응답 크기를 제한한다. 실제 자격증명으로 STOVE → UGS 연속 인증을 성공시키기 전에는 배포 검증 완료로 간주하지 않는다.

서버 소유권 검증은 아직 구현하지 않았다. 클라이언트 SDK 소유권 확인에 더해 구매 권한을 서버에서 강제할 필요가 있는지 STOVE 측과 확인한다. 정책 변경·키 교체·제재 처리·모니터링과 가용성은 운영 준비 항목이다.
